## 二、反例搜索（这是本条最该验的地方）

修法是"先剔除 `data:…;base64,` 载荷再查"，风险点是**把真故障一起剔掉了**。我做了两个反向实验：

1. **纯矢量文件里注入真 NaN**：把 `bg_luding.svg` 复制到 `tmp/q11/bad.svg`，把 `width="1920"` 改成 `width="NaN"`

```
> node tools/validate-svg.js tmp/q11
[validate-svg] 4 个文件有问题：
  × tmp/q11/bad.svg        - 含 NaN 数值
  × tmp/q11/bg_broken.svg  - 含 NaN 数值
  × tmp/q11/bg_du.svg      - 含 undefined
  × tmp/q11/fill.svg       - 含空 fill=""
exit=1
```

（后三个是作者自己的负例文件，留在 `tmp/`，`tmp/` 已被忽略。）

2. **含 581 KB base64 的文件里注入真 NaN**（修复的薄弱点：剔除 base64 后是否还查得到真值属性）

```
> node tools/validate-svg.js tmp/q11/b64bad.svg
[validate-svg] 1 个文件有问题：
  × tmp/q11/b64bad.svg     - 含 NaN 数值
exit=1
```

**结论：守卫恢复了（干净树 exit 0），真故障三种类型（NaN / undefined / 空 fill）仍然抓得住，且不受内嵌 base64 影响。**
